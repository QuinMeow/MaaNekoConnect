# 每日任务与 Soleil

## 当前方向与边界

2026-10-20 本轮将旧「每日任务：免费优先」总入口拆成独立玩法模块，在 [interface.json](../../../assets/interface.json) 的任务列表中由用户选择、排序，领奖放最后。业务共享判页及安全收尾适配位于 [daily_core.json](../../../assets/resource/pipeline/daily_core.json)，已知页面归首页由 [navigation.json](../../../assets/resource/pipeline/navigation.json) 统一执行，各玩法由独立 `daily_*.json` 执行；[delivery.py](../../../agent/delivery.py) 仅汇总原生地图识别、保存当前 pin 并核验派出状态。

按用户要求，旧 `daily.json` 总流程及每日业务 CLI 已删除，不保留进度扫描兼容入口或另一套命令行任务编排。本文中的旧 CLI 报告与退出状态只用于解释已保存的历史证据，不代表当前仍支持该工具。

**本轮模块是用户主动选择的操作，不再按每日列表 `0/1` 筛掉已选择的模块。** 即使账号已 `9/9`，选择 VR、比赛、配送、礼物或交换仍可能实际消耗免费次数或游戏资源。任务执行结束、回到首页、MaaFramework job 成功，不等于每日条件、全部邮件或所有订单已完成。

目标始终为 `127.0.0.1:5557`，不提供设备回退。游戏事实来源为 2026-10-19 至 20 日、2.2.0 / JP2、日文 720 x 1280 的[人工研究](daily_tasks_research.md)与本机截图；刷新时刻由用户提供为东京 00:00 / 北京 23:00，各玩法独立额度仍按当前游戏画面读取。

2026-10-21 任务列表整理为 12 个入口：11 个其他每日模块，加一个 `Soleil`。Soleil 的复选框包含配送、浴室收菜、当番换班和家具升级，默认勾选前三项。家具原有排序、筛选、依頼、轮数及间隔配置均保留，勾选家具升级后显示；配送原内部入口仍用于业务复用。

## 模块选择

Interface 及各 pipeline 入口的 `doc` 统一使用操作名称，例如“VR猫爬塔”“交换所兑换”，不把金额、次数或每日完成条件写进名称；具体限制仍保留在说明和消费 Gate 中。“框架测试”已从正式任务列表与资源中移除；独立启动截图脚本仅在显式运行时注入自己的诊断流程，不属于用户任务。

### 运行日志

入口、关键操作、结果和异常使用 Pipeline `focus` 的 `Node.Action.Succeeded` / `Node.Action.Failed` 消息。日志只保留简短操作、数值和失败原因，例如“[配送] 订单已开始”“[浴室] 鸭子+3”。普通候选未命中不逐帧输出，已删除重复的防御性说明。

配送分类、领取钻石、家具等级和最大耗时尚未识别时，直接输出对应字段“未识别”。鸭子增量、原有订单核对、免费次数和倒计时使用实际识别结果。客户端使用前停止任务、重启 Agent 并重载资源。

浴室每次点击前以原生模板确认顶部鸭子图标，再用原生 OCR 读取当前余额。领取后仍须先确认入浴次数恰好减一及原角色标记消失，最多等待 3.5 秒重新读取结果；前后余额差为 `1..10` 才输出单次 `鸭子 +N`、前后读数和本任务已确认累计。单次随机 `1..10` 是用户于 2026-10-21 提供的规则，不代表本次采样已覆盖全部奖励值。余额缺失、歧义或差值超界则明确输出“鸭子增量未确认”，不当作 `0`、不编造随机数，也不为补读重复点击；有未知结果时累计只声称已确认的部分。

领取确认与下一名点击之间有独立 `Soleil_BathLog` 节点，将动态结果通过 `focus` 输出到前端，不只写 Agent 标准输出。日志准备或状态保存失败时不能清除待确认许可并继续点击；读鸭子余额本身不替代原有领取确认，也不增加领取预算。剩余入浴为零时只检查收尾，不输出伪造的“获得0鸭子”。

### 配送收敛条件

[daily_delivery.json](../../../assets/resource/pipeline/daily_delivery.json) 控制批量领取、自动编队、派单及免费/可选付费刷新；`DailyDeliveryMapProbe` 在当前 Task 的 Context 中保存选中 pin、已派出坐标和刷新前地图快照，只汇总原生模板/OCR 结果，不执行点击或另建业务调度器。`OrderCount` 必须完整读为 `0/18` 至 `18/18`，且去重后的可见订单 pin 数必须与它一致；未知、互相矛盾或漏识别的标记均停止，不能以“没有识别到待派单”推断全部已派出。

派出后的 `DailyDelivery_Verify` 明确为 `DoNothing`，只读取总览中所选订单上方的倒计时。已确认派出的坐标保存在 `started`，后续动画帧漏识别时不会再次选中；倒计时胶囊扩大检查范围，并增加左右边缘模板。刷新前以 `refresh_seen` 保存全部旧订单的位置，确认出现快照以外的新待派订单后才继续，保留仍在图上的旧运行订单记录。100 钻选项默认关闭，每任务最多一次；付费资格要求每单自己的唯一计时胶囊及数字区域，不使用宽区域回退，也不能让两单共用同一计时区域。

2026-10-20 用户确认订单为 food、sweets、drive 三类，各有五种底色。Agent 提取深棕色主体、轻微平滑抗锯齿后交给原生模板匹配，复用三种主体及呼吸动画尺寸，不维护十五套业务分支。汉堡右侧局部模板覆盖已观测的倒计时遮挡，数量一致性检查仍保留。五色组合测试是合成底色验证，并非十五种实机图标均已采集。每个 pin 的倒计时/完成文字合并为一次原生 OCR，不再分别扫描两遍；同一标签含多个不同结果、无法读出的标签仍停止。全在配送中属于正常无待派单状态，不等于识别失败；是否免费更新仍由当前按钮独立确认。

随后实机确认顶部运行订单的倒计时会覆盖总数，地图也不响应横移。总数可读时仍严格核对 OCR 数量；不可读时，仅在该区域同时识别到倒计时框和完整时间文字，才启用独立的订单尾部轮廓匹配。轮廓和主体必须数量相同、在 `1..18` 范围内且逐个唯一配对，再逐个确认状态。不缓存历史总数、不把识别失败当空地图；总数可读但不一致、未知遮挡、轮廓或主体缺失仍停止。备用判据是有限实机样本下的双重视觉检查，不等于所有游戏版本/遮挡形态都已验证。

相邻倒计时也可能遮住汉堡右下角，因此主体补充左侧局部模板，与既有右侧模板共用去重。局部模板的中心差在呼吸动画下略大于 20 像素，单帧去重、跨帧已派单记录及刷新快照匹配统一使用 24 像素；派送前后选中位置核对仍为 20 像素。扫描遇到无法确认的动画帧可走 `DailyDelivery_RetryScan`，只等待、重新识别，整个 Task 共用六次额度，耗尽截图停止；不重放已派送订单、不重置消费/恢复预算。派送后复核仍单独有界，失败不能回到消费节点重试。

### 变化图标与每日限次

收入入口仅在正向确认明亮首页后打开一次，不依赖随积攒时间变化的金币气泡。真正领取仍要求收入弹窗标题与关闭控件同时满足，未知弹窗不领取、不重复打开。VR 将易变的免费文字图片改为精确 OCR，仍同时要求 VR 判页、明亮按钮、免费标签与精确剩余次数，继续保留消费后严格减一确认。

用户于 2026-10-20 确认社团问候一天一次。一次问候后等待五秒，没有奖励时仅在再次确认正常成员页后返回首页，作为无新增奖励收尾；未知页面仍停止，不重复问候，也不声称获得奖励。

每单须有电池图标、白名单成本和可用配达按钮，默认最多派出 36 单，开启 100 钻更新后最多 54 单，选择、编队和派送三个节点同步限制。`10000` 是每单电池上限，不是本批总上限。点击配达后等待总览中该单出现倒计时或完成状态，再选择下一单。

默认只进行一次每日免费更新。启用付费更新后，所有可见订单须非空且逐项确认正在配送，入口还须识别 `100`、宝石图标和“依頼更新”。提交前再次核对完整 100 钻更新说明、独立金额、宝石及红色“確定”按钮；入口和提交分别最多一次。确认后只读核对新地图，再派出新增订单，批次结束直接返回，不再进入刷新检查。关闭选项显式恢复 36 单预算，运行中恢复不会重置这些计数。

VR 的次数证明由纯 JSON 的 `DailyVR_ReadN` 与 `DailyVR_VerifyN` 完成：本次先精确读取 `1` 至 `9`，绑定唯一预期余量后才进入共同消费节点；结果领取后只接受这次预期的 `N-1`，不能自由重新选择更大读数。2026-10-20 实机确认最后一次免费用完后标签消失而非显示零，因此仅在先前确认为一次、领奖结束后的 Verify0 允许明亮 VR 页、无气泡蓝色区域和跳过按钮文字共同确认后返回，不再消费。其余次数不变、跳减、增加或缺失仍截图停止。

### 排序与停止

通过 Interface 任务列表选择、排序所需模块；需要领奖时将领奖放在所选玩法之后，不自动补选其他模块。每个模块都有独立入口与自己的有界执行条件，不再通过旧每日完成度总入口调度。

登录可单独选择或放在所选序列开头；后续每个模块仍自行调用公共导航，不能依赖此前已经运行登录模块。登录只清理登录奖励/公告，不等于领取日常列表中的登录条件奖励，后者属于显式选择的领奖任务。模块的正常结束、受限退出或公共恢复不能仅凭前端“已完成”判为业务成功；结果未确认时停止并核对，不重试消费来补做。

### 登录条件启动

`DailyLogin_Start` 先通过 [login.py](../../../agent/login.py) 的 `DailyLoginAppState`，使用当前已绑定的 Maa 控制器只读执行 `dumpsys activity activities`，不另建 ADB 连接、不选设备或调用主机 shell。只接受一致的 `topResumedActivity` / `mResumedActivity` / `ResumedActivity` 包名，不从历史 Activity 中猜前台。游戏已在前台时直接等待已知 UI；确认前台为其他应用时，原生 `DailyLogin_Launch` 对精确游戏包调用 `StartApp`，每 Task 最多一次，不调用 `StopApp`。这既涵盖已退出后的冷启动，也涵盖从后台切回。

每次系统查询上限三秒，并检查返回状态与取消；未知、失败、歧义或不支持的控制器不能放行启动。初始状态扫描上限十秒，启动后等游戏成为前台上限四十五秒，之后 `DailyLogin_WaitUi` 最多一百二十秒只等待已知页面，再交公共导航。这个额外等待修复了实机冷启动白色 Loading 超过原三十秒导航窗口的问题：未知启动画面只等，不盲点、不中途强制重启。异常发生时仍由既有公共恢复处理，不新增重启预算。

独立模块分别是 MaaFramework Task，次数许可主要在各 Task 内生效，不是跨进程的持久账号预算。不要用重启进程、新建 Task 或重跑失败任务来刷新预算；消费结果不确定时先核对游戏状态和运行记录。
